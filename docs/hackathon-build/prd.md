# QuietPilot 제품 요구사항 문서

## 제품 요약

QuietPilot은 여러 디지털 서비스와 생활 기기를 사용하는 사람이 반복되는 일을 직접 발견하고, 앱마다 옮겨 다니며 정리하고, 자동화 규칙을 일일이 만드는 부담을 줄여 주는 모바일 중심 생활 에이전트다.

사용자는 필요한 연결만 허용한다. QuietPilot은 허용된 범위에서 실제로 볼 수 있는 신호와 실행 가능한 동작을 조사하고, 관련된 정보를 하나의 **Case** 또는 **Routine 제안**으로 정리한다. 사용자가 직접 내린 요청도 같은 흐름으로 처리한다. 에이전트는 내부 작업을 세부 단계로 분해하되, 그 미세한 작업 목록을 사용자에게 떠넘기지 않는다. 사용자는 결과, 근거, 위험, 권한과 다음 결정만 본다.

QuietPilot의 핵심은 무제한 자동화가 아니라 **설명 가능한 점진적 위임**이다. 안전하고 되돌릴 수 있는 준비 작업은 허용된 범위에서 진행할 수 있지만, 외부 상태를 바꾸거나 위험이 커지는 동작은 정책에 따라 승인을 받는다. 결제, 삭제, 민감정보 전송, 최종 제출처럼 영향이 큰 동작은 반복 허용으로 전환하지 않고 항상 별도 승인을 요구한다.

## 제품 용어

- **후보:** 연결된 신호에서 사용자가 얻을 결과와 QuietPilot이 준비할 수 있는 동작이 함께 확인된, 아직 선택되지 않은 제안이다. 단순 메일·이벤트·요약은 후보가 아니다.
- **Case:** 한 가지 결과를 목표로 하는 제한된 작업 단위다. 근거, 계획, 권한 상태, 실행 상태와 감사 기록을 가진다.
- **Routine:** 조건이 맞을 때 Case를 만들거나 진행시키는 재사용 규칙이다. 제안되었다는 이유만으로 활성화되지 않는다.
- **진행:** 사용자의 결정이 필요하거나 현재 실행 중인 Case를 모은 상위 영역이다.
- **새 제안:** QuietPilot이 잡음을 제거하고 실행 준비까지 끝낸 후보만 결과별로 보여 주는 상위 영역이다.
- **정책:** 어떤 신호를 읽고 어떤 동작을 한 번, 조건부 또는 반복적으로 허용할지 정한 사용자 규칙이다.

## 목표 사용자

주 사용자는 이메일, 일정, 할 일, 스마트홈 같은 서비스를 여러 개 쓰지만 자동화 규칙을 직접 만들고 지속적으로 관리하고 싶지는 않은 일반 사용자다. 학생, 개발자, 독립 작업자와 바쁜 가정은 좋은 초기 사례이지만 특정 직업이나 생활 형태만을 대상으로 하지 않는다.

이 사용자는 다음을 원한다.

- 연결만 하면 가능한 일을 에이전트가 먼저 발견해 주기를 원한다.
- 제안이 많아져도 중요한 결정과 실행 중인 일은 놓치고 싶지 않다.
- 왜 제안되었고 무엇이 바뀌는지 이해한 뒤 권한을 주고 싶다.
- 긴 채팅이나 미세한 작업 목록을 관리하지 않고 결과 중심으로 위임하고 싶다.
- 자동으로 진행되더라도 언제든 상태를 확인하고 중지하거나 권한을 회수하고 싶다.

## 제품 경험 원칙

1. **수집과 발견을 분리한다.** 연결 신호는 사용자 작업 목록이 아니다. 명확한 결과와 지원되는 다음 동작이 모두 있을 때만 후보가 되며, 후보 발견만으로 푸시 알림을 보내지 않는다.
2. **상태와 아이디어를 분리한다.** `진행`에는 결정 필요와 실행 중인 Case만, `새 제안`에는 아직 선택하지 않은 후보만 표시한다.
3. **상세 작업은 에이전트가 흡수한다.** 사용자에게는 결과 단위의 계획과 필요한 결정만 보여 준다.
4. **권한은 눈에 보여야 한다.** 한 번, 조건부, 반복 허용의 범위와 해제 방법을 승인 전에 설명한다.
5. **권한 확장은 자동으로 일어나지 않는다.** 계획, 데이터 출처, 외부 동작, 위험 또는 권한이 실질적으로 바뀌면 다시 확인받는다.
6. **실행 요청 수락과 완료를 구분한다.** 외부 서비스가 요청을 받았다는 응답만으로 완료 처리하지 않고 결과 상태를 확인한다.
7. **초보자가 분류 작업을 떠안지 않는다.** 기본 화면은 검색·위험 필터·체크박스·다중 선택 없이 결과, QuietPilot이 준비할 동작과 한 번의 결정부터 보여 준다. 기술 근거와 고급 정리는 필요할 때만 펼친다.
8. **모델 판단과 실행 권한을 분리한다.** 스팸·스미싱 판별이나 일정 추출 모델은 근거와 신뢰도를 제안한다. 자동 실행은 발신자·날짜·링크·결제·중복·사용자 정책을 확인하는 결정론적 계층이 별도로 허용한다.
9. **개인화와 권한을 분리한다.** 승인·수정·숨김·중지 기록은 무엇을 먼저 발견하고 보여 줄지 개선하지만, 실행 허용 범위나 위험 상한을 자동으로 넓히지 않는다.

## 핵심 사용자 여정

1. 사용자가 앱을 열고 로그인하거나 가입한다.
2. 사용자가 Gmail, Google Calendar 또는 Tasks, SmartThings, Android 문자 등 원하는 연결을 선택한다. 문자 연결은 실제 배포 경로에서 허용되는 권한과 대안을 먼저 설명한다.
3. QuietPilot은 연결별로 읽을 정보와 수행할 수 있는 동작을 구분해 보여 주고, 사용자는 필요한 범위만 허용한다.
4. 연결 직후 QuietPilot은 기본적으로 최근 7일 범위를 먼저 살피고 이후 새 신호를 계속 확인한다. 범위는 연결별로 조정할 수 있다.
5. 분석 결과는 전체 스캔이 끝날 때까지 기다리지 않는다. 에이전트는 신호가 단순 인사·뉴스레터·홍보·참고용 알림인지 먼저 판단하고, 필요한 경우 일정·마감·명시적 답변 요청 중 하나의 결과와 1~3개 실행 준비 동작을 만든다.
6. 지원 capability, 최소 신뢰도와 위험 검증을 통과한 후보만 `새 제안`에 들어간다. 낮은 신뢰도나 실행 동작이 없는 신호는 사용자에게 검토 작업으로 넘기지 않는다.
7. QuietPilot은 같은 결과의 후보를 먼저 중복 제거·묶음 처리하고, 첫 화면에는 각 묶음의 우선 후보만 보여 준다. 사용자는 `이대로 준비`, `내용 조정`, `필요 없음` 중 하나만 고르면 된다.
8. 사용자가 후보를 준비하도록 선택하면 후보에 이미 연결된 동작과 근거가 하나의 결과 중심 Case로 이동한다. 서로 다른 영향이나 권한은 동의 없이 합치지 않는다.
9. 사용자가 직접 원하는 일을 입력하면 QuietPilot은 연결 신호와 같은 Case 흐름에 넣고, 필요한 맥락을 수집한 뒤 하나의 제한된 계획을 보여 준다.
10. 사용자는 제안 이유, 근거, 예상 결과, 위험도, 필요한 권한과 되돌리는 방법을 확인하고 허용 범위를 선택한다.
11. 허용된 안전 작업은 실행되고 `진행`에서 상태를 볼 수 있다. 새로운 결정이 필요하거나 외부 동작이 바뀌면 Case가 `결정 필요` 상태가 된다.
12. 사용자는 Case 상세에서 타임라인, 사용된 근거, 완료된 준비 작업, 남은 결정과 결과 확인 상태를 본다. Case별 채팅으로 계획을 보완할 수 있다.
13. 작업 결과가 확인되면 Case는 기록으로 이동한다. 사용자는 결과와 권한을 검토하고 반복 규칙을 유지, 수정 또는 해제할 수 있다.

## 정보 구조

### 1. 진행

`진행`은 현재 사용자가 신경 써야 하는 일만 모은다.

- `결정 필요` Case를 먼저 표시한다.
- 그 아래에 실행, 대기, 결과 확인 중인 Case를 표시한다.
- 각 Case는 제목, 목표 결과, 현재 상태, 왜 지금 보이는지, 위험도, 최근 변화와 다음 동작을 요약한다.
- 일반적인 내부 분석 단계는 접힌 타임라인에 두고 홈에 노출하지 않는다.
- 완료, 중지, 실패 또는 권한 회수된 Case는 별도 기록에서 찾는다.

### 2. 새 제안

`새 제안`은 에이전트가 이미 선별하고 실행 준비한 소수의 결과를 결정하는 영역이다.

- 모든 후보는 일정, 마감, 답변처럼 사용자가 얻을 결과와 QuietPilot이 준비할 동작을 함께 가진다.
- 같은 결과의 후보는 한 기본 묶음에만 속하며 첫 화면에는 최대 세 개의 우선 후보만 펼친다.
- 기본 화면은 검색, 위험 필터, 체크박스와 다중 선택을 요구하지 않는다. 더 보기와 기술 근거는 보조 경로다.
- 각 카드의 첫 정보는 `왜 지금`, `QuietPilot이 준비할 작업`, `이대로 준비 / 내용 조정 / 필요 없음`이다.
- 신뢰도 0.70 미만, 지원 capability가 없는 동작, 불명확한 참고 메일은 `검토 대기`에 넣지 않고 발견 단계에서 보류한다.
- 후보 발견 자체에는 배지나 푸시 알림을 사용하지 않는다.

## Epics와 사용자 이야기

### Epic 1: 안전한 시작과 연결

#### 이야기 1.1 — 필요한 연결만 허용하기

사용자로서, 각 서비스에서 QuietPilot이 읽고 실행할 수 있는 범위를 따로 확인하고 연결하고 싶다. 그래야 필요 이상의 권한을 주지 않고 시작할 수 있다.

수용 기준:

- 연결 전 화면에서 읽기 권한과 실행 권한이 구분되어 보인다.
- 지원하지 않는 데이터나 동작은 연결 가능한 것처럼 표시하지 않는다.
- 사용자는 하나의 연결만으로도 시작할 수 있고 나머지는 나중에 추가할 수 있다.
- 연결을 해제하면 새 데이터 수집이 중단되고, 기존 Case에 미치는 영향이 설명된다.
- 기기나 항목이 서비스 앱에는 있지만 QuietPilot에서 접근할 수 없으면 `연결됨`이 아니라 `현재 접근 불가`로 표시한다.

#### 이야기 1.2 — 연결 직후 점진적으로 결과 보기

사용자로서, 연결이 끝난 뒤 긴 전체 분석을 기다리지 않고 먼저 확인된 결과부터 보고 싶다. 그래야 앱이 실제로 무엇을 찾는지 바로 이해할 수 있다.

수용 기준:

- 최초 분석 범위가 기본 최근 7일임을 보여 주고 연결별로 바꿀 수 있다.
- 분석 중인 연결, 완료된 연결과 오류가 난 연결을 구분해 보여 준다.
- 최근 7일 결과는 Gmail의 모든 응답 페이지와 각 페이지의 분석이 끝난 뒤에만 완료로 표시한다. 첫 페이지나 최신 일부 메일을 전체 확인 결과로 표현하지 않는다.
- `연동 중`, `확인 중`, `할 일 있음`, `확인 완료·할 일 없음`, `확인 실패/다시 확인 필요`를 연결별로 표시한다. 전체 빈 후보 수로 연결 상태를 대신하지 않는다.
- 하나의 근거 있는 후보가 준비되면 전체 분석 완료 전에 `새 제안`에 나타난다.
- 한 페이지에 여러 독립적인 실행 가능 메일이 있으면 각각의 결과를 후보로 만들 수 있으며, 잡음 메일 하나 때문에 같은 묶음의 다른 메일까지 함께 억제하지 않는다.
- 분석 중 후보가 하나도 없으면 빈 화면 대신 현재 확인한 범위와 다음 확인 시점을 보여 준다.
- `준비할 일 없음`은 연결과 분석이 완료되고 현재 발견 기준의 후보 응답까지 성공한 경우에만 표시한다. 응답 오류, 이전 발견 기준 또는 아직 끝나지 않은 분석은 빈 결과로 처리하지 않는다.
- 후보 생성은 기본적으로 푸시 알림을 발생시키지 않는다.

#### 이야기 1.3 — 자연어와 UI로 범위 정하기

사용자로서, “수업과 마감 관련 메일만 봐줘”처럼 짧게 말하거나 화면의 필터로 관심 범위를 조정하고 싶다. 그래야 복잡한 규칙을 처음부터 직접 만들지 않아도 된다.

수용 기준:

- 사용자의 자연어 요청은 출처, 주제, 시간, 위험과 허용 동작으로 해석된 요약을 보여 준다.
- 해석된 범위는 수정 가능한 UI 정책으로 표시된다.
- 새 제안에서 비슷한 후보 줄이기나 범위 조정을 선택하면 관련 정책의 변경 전후가 보인다.
- 범위 변경이 기존 실행 권한을 넓히면 자동 적용하지 않고 별도 확인을 요청한다.

#### 이야기 1.4 — 문자 속 미래 일정을 안전하게 자동 알림으로 만들기

사용자로서, 예약·방문·수령·마감 문자를 매번 직접 캘린더나 알람으로 옮기지 않고 싶다. 스팸이나 위험한 문자는 건드리지 않으면서, 내가 미리 허용한 좁은 범위의 확실한 일정만 QuietPilot이 알아서 로컬 알림으로 등록해 주기를 원한다.

수용 기준:

- 연결 전에 과거 문자 접근, 새 알림 관찰, 선택 문자 공유처럼 실제로 사용할 입력 방식과 권한 차이를 설명한다.
- 문자 원문은 기본적으로 온디바이스에서 분류·추출하며, 서버에는 필요할 때 날짜, 사건 유형, 발신자 분류, 신뢰도와 출처 참조 같은 최소 정규화 정보만 전달한다.
- 전담 Message Safety Analyst는 `정상 일정`, `검토 필요`, `스팸·스미싱 의심`과 근거를 반환하지만 실행 허용을 직접 결정하지 않는다.
- 신뢰 발신자, 명확한 미래 날짜·시간, 의심 링크·결제·OTP 부재, 비중복, 활성 저위험 정책을 모두 만족할 때만 취소 가능한 로컬 알림을 사람의 추가 입력 없이 등록할 수 있다.
- 날짜가 여러 개이거나 시간대가 모호한 문자는 `결정 필요`, 의심 링크·결제·OTP·스미싱 문자는 격리 또는 무시하며 자동 알림·링크 열기·답장을 하지 않는다.
- 같은 사건을 다시 받으면 기존 알림과 Case를 갱신하고 중복 알림을 만들지 않는다.
- 사용자가 정책을 해제하면 새 문자 자동 등록은 즉시 중단된다. 이미 만든 알림을 취소하는 동작은 영향 범위를 보여 준 뒤 별도로 처리한다.
- 전체 과거 SMS 읽기가 Google Play 제한 권한 심사를 통과하지 못하면 선택 공유/import 또는 향후 알림 관찰 경로로 기능을 축소하고, 지원 범위를 숨기지 않는다.

### Epic 2: 많은 새 제안 정리하기

#### 이야기 2.1 — 에이전트가 선별한 실행 가능 제안 보기

사용자로서, 받은 메일을 다시 분류하지 않고 QuietPilot이 실제로 대신 준비할 수 있는 결과만 보고 싶다. 그래야 앱이 또 하나의 받은편지함이 되지 않는다.

수용 기준:

- Candidate마다 한 가지 사용자 결과와 1~3개의 typed Action proposal이 있다.
- 인사, 사교 메일, 일반 뉴스레터, 홍보, 참고용 알림과 미래 의무가 없는 영수증은 Candidate를 만들지 않는다.
- Candidate의 모든 Action은 현재 AVAILABLE capability operation과 정확히 일치한다.
- `새 제안`의 모든 후보는 최소 하나의 결과 그룹 아래 표시되고 첫 화면은 그룹당 세 개까지만 펼친다.
- 같은 후보가 여러 그룹에 중복 카드로 나타나지 않는다.
- 결과나 동작이 불확실하면 사용자 검토함을 만들지 않고 에이전트가 abstain한다.

#### 이야기 2.2 — 한 번의 선택으로 준비 시작하기

사용자로서, 에이전트가 준비할 내용을 먼저 보고 한 번의 선택으로 맡기거나 조정하고 싶다. 그래야 후보를 고른 뒤 다시 작업을 설계하지 않아도 된다.

수용 기준:

- 카드에 결과, 지금 제안한 이유와 QuietPilot이 준비할 동작이 먼저 보인다.
- 기본 선택지는 `이대로 준비`, `내용 조정`, `필요 없음`이다.
- `이대로 준비`는 한 Candidate만 원래 근거·Action과 함께 Case로 이동시킨다.
- `내용 조정`은 같은 Case에서 자연어로 결과·시간·범위를 바꾸게 하고 실행 전에 수정 계획을 다시 보여 준다.
- 검색, 정렬, 위험 필터와 다중 선택은 기본 흐름에 나타나지 않는다.

#### 이야기 2.3 — 원하지 않는 제안 줄이기

사용자로서, 필요 없는 제안을 한 번에 없애고 그 선택이 다음 발견에 반영되기를 원한다. 그래야 분류 규칙을 직접 관리하지 않아도 앱이 조용해진다.

수용 기준:

- 후보 카드에 `필요 없음`이 명확히 보이고 상세 메뉴를 찾지 않아도 된다.
- 선택은 현재 후보를 즉시 숨기며 structured negative feedback으로 기록한다.
- 반복된 부정 기록은 discovery ranking과 suppression에만 쓰고 연결 범위나 실행 권한을 바꾸지 않는다.
- 숨긴 후보는 기록에서 확인할 수 있지만 기본 그룹에는 다시 나타나지 않는다.
- 새로운 강한 근거 때문에 유사 후보가 다시 나타나면 이전과 달라진 이유를 설명한다.

#### 이야기 2.4 — 실제 capability에서 Routine 제안 받기

사용자로서, 연결된 신호와 실행 가능한 동작을 바탕으로 반복 가능한 Routine을 제안받고 싶다. 그래야 내가 직접 트리거와 동작을 처음부터 조합하지 않아도 된다.

수용 기준:

- Routine 제안은 사용 가능한 실제 신호, 조건과 동작을 근거로 한다.
- 제안은 트리거, 조건, 수행할 동작, 위험, 필요한 권한과 해제 방법을 보여 준다.
- 제안만 생성된 상태에서는 Routine이 활성화되지 않는다.
- 사용자가 허용 범위를 선택한 뒤에만 활성 상태로 바뀐다.
- 모바일 앱에만 보이고 공개 API로 접근할 수 없는 Routine이나 기기를 QuietPilot이 제어 가능한 것으로 표현하지 않는다.

#### 이야기 2.5 — 이전 결정으로 발견 적중도 높이기

사용자로서, 내가 자주 승인하고 실제로 유용했던 작업은 더 빨리 발견하고, 자주 숨기거나 중지한 제안은 덜 보고 싶다. 그래야 QuietPilot을 오래 사용할수록 직접 프롬프트하거나 불필요한 후보를 정리하는 횟수가 줄어든다.

수용 기준:

- `승인 후 결과 확인`, `승인 뒤 계획 수정`, `이번만 숨기기`, `비슷한 제안 줄이기`, `보류`, `중지`, `권한 회수`, `되돌리기`를 서로 다른 의미의 피드백으로 기록한다.
- 단순 승인 한 번을 성공으로 보지 않는다. 큰 수정 없이 승인되고, 외부 결과가 확인되며, 짧은 후회·취소 관찰 구간에도 유지된 경우를 강한 긍정 신호로 사용한다.
- 보류는 거절로 해석하지 않고 시간·상황 신호로만 사용한다. 계획 수정은 원래 제안보다 사용자가 남긴 수정 feature를 더 강한 근거로 사용한다.
- 개인화에는 원문 메일·문자·전화번호·민감한 Action parameter를 복제하지 않고 출처 유형, 사건 분류, 주제 tag, 시간 범위, 위험, 동작 유형, 검증 결과 같은 최소 구조화 feature만 사용한다.
- 개인화 점수는 Candidate 탐색, 기본 그룹과 그룹 안 순서에만 영향을 준다. Approval, Policy, risk ceiling, plan hash와 executor 허용 여부에는 직접 입력되지 않는다.
- 반복된 긍정 기록은 standing 권한을 만들지 않고, 조건과 영향 범위를 보여 주는 Routine 제안만 생성한다.
- 각 개인화 후보는 `최근 승인한 일정 준비와 비슷해요`처럼 왜 우선 표시됐는지 설명한다. 사용자는 학습에 사용된 범주를 확인하고, 특정 신호를 제외하거나 개인화를 초기화할 수 있다.
- 오래된 선호에는 시간 감쇠를 적용하고, 이미 학습된 범주만 반복하지 않도록 소량의 탐색 후보를 유지한다.
- 발견 품질은 `큰 수정 없이 승인 + 결과 확인 + 후회·취소 없음` 비율, 상위 후보 정밀도, 숨김·억제율, 결정까지 걸린 시간과 다양성으로 평가한다.

### Epic 3: 후보와 직접 요청을 Case로 만들기

#### 이야기 3.1 — 연결 신호를 하나의 Case로 묶기

사용자로서, 서로 관련된 이메일·일정·기기 신호가 하나의 결과 중심 Case로 정리되기를 원한다. 그래야 같은 일을 여러 알림과 카드로 중복 처리하지 않아도 된다.

수용 기준:

- 관련 신호는 하나의 Case에서 각각의 출처와 관계를 보여 준다.
- 같은 사건에서 파생된 중복 후보는 별도 Case로 만들지 않는다.
- 서로 충돌하는 근거가 있으면 한쪽을 임의로 선택하지 않고 `결정 필요`로 표시한다.
- Case는 사용자가 이해할 수 있는 목표 결과를 제목과 요약으로 가진다.
- 내부 작업 분해는 기본 화면에서 접혀 있고 필요할 때만 펼칠 수 있다.

#### 이야기 3.2 — 직접 요청을 같은 흐름으로 위임하기

사용자로서, 원하는 일을 짧게 말하면 QuietPilot이 연결된 맥락을 찾아 하나의 계획으로 정리해 주기를 원한다. 그래야 일반 에이전트처럼 자유롭게 요청하면서도 권한과 실행 상태를 추적할 수 있다.

수용 기준:

- 직접 요청을 보내면 하나의 새로운 Case가 생성된다.
- Case는 이해한 결과, 사용할 연결, 준비할 일과 승인이 필요한 동작을 요약한다.
- 필요한 연결이 없으면 가능한 준비 작업과 막힌 실행 작업을 구분해 보여 준다.
- 사용자에게 미세한 작업을 하나씩 다시 묻지 않고, 관련 결정을 하나의 결과 중심 질문으로 묶는다.
- 요청을 취소하면 아직 수행하지 않은 외부 동작은 실행되지 않는다.

#### 이야기 3.3 — 관련 신호를 표시 전에 하나의 결과로 묶기

사용자로서, 같은 사건의 여러 메일이나 변경 알림을 직접 골라 묶지 않고 하나의 제안으로 받고 싶다. 그래야 중복 정리를 떠안지 않는다.

수용 기준:

- QuietPilot은 동일 entity, 날짜, 동작과 evidence fingerprint를 기준으로 표시 전에 중복 신호를 묶는다.
- 합쳐진 후보는 목표, 달라진 내용과 필요한 동작을 하나의 카드로 보여 준다.
- 위험 수준이나 외부 효과가 다른 후보는 자동으로 하나로 합치지 않는다.
- 사용자가 `이대로 준비`를 선택하기 전에는 실행 동작이 발생하지 않는다.
- 합친 뒤에도 각 신호의 원래 근거는 Case 상세에서 추적할 수 있다.

### Epic 4: 설명 가능한 승인과 점진적 자동화

#### 이야기 4.1 — 승인 전에 결과와 영향 이해하기

사용자로서, 무엇이 왜 실행되고 어떤 데이터와 권한을 쓰는지 확인한 뒤 승인하고 싶다. 그래야 편리함을 얻으면서도 통제권을 유지할 수 있다.

수용 기준:

- 승인 화면에 제안 이유, 근거 출처, 예상 결과, 외부 변화, 위험도, 가역성과 권한 해제 방법이 보인다.
- 실행할 대상과 값이 정해진 경우 정확한 대상과 변경 값을 보여 준다.
- 한 번 허용, 조건부 허용, 반복 허용 중 가능한 선택만 표시한다.
- 고위험 동작에는 반복 허용이나 무승인 실행 선택이 나타나지 않는다.
- 거절 또는 보류를 선택해도 이미 안전하게 완료된 준비 작업과 남은 작업이 구분된다.

#### 이야기 4.2 — 계획이 바뀌면 다시 확인하기

사용자로서, 승인한 뒤 실행 내용이나 권한이 달라졌다면 자동으로 계속되지 않고 변경점을 확인하고 싶다.

수용 기준:

- 대상, 외부 동작, 요청 권한, 위험 수준 또는 중요한 근거가 바뀌면 기존 승인이 더 이상 유효하지 않다.
- 변경 전후가 비교되어 보이고 다시 승인이 필요한 이유가 설명된다.
- 재승인 전에는 새 외부 동작이 실행되지 않는다.
- 단순한 내부 순서 변경처럼 결과와 권한에 영향을 주지 않는 변화는 재승인을 요구하지 않고 기록만 남긴다.
- 사용자는 변경 계획 승인, 원래 계획 유지가 가능한 경우 그 선택, 보류 또는 중지를 선택할 수 있다.

#### 이야기 4.3 — 반복 허용과 조건부 허용 관리하기

사용자로서, 안전한 반복 동작은 조건을 정해 자동화하고 언제든 해제하고 싶다.

수용 기준:

- 반복 또는 조건부 허용에는 대상, 시간·상태 조건, 만료 여부와 최대 영향 범위가 표시된다.
- 사용자가 이전에 여러 번 같은 방식으로 승인해도 QuietPilot이 권한을 자동 승격하지 않고 Routine 제안만 만든다.
- 활성 정책 목록에서 허용 범위와 최근 사용 기록을 확인할 수 있다.
- 정책을 해제하면 미래 실행이 중단되고, 이미 실행 중인 Case는 다음 외부 동작 전에 일시 정지된다.
- 정책 조건을 벗어난 Case는 자동 실행하지 않고 `결정 필요`로 이동한다.

### Epic 5: 실행과 모니터링

#### 이야기 5.1 — 진행 중인 일만 한곳에서 보기

사용자로서, 결정이 필요한 Case와 실행 중인 Case를 `진행`에서 함께 보고 싶다. 그래야 새 아이디어 사이에서 현재 작업을 놓치지 않는다.

수용 기준:

- `진행`과 `새 제안`이 두 개의 상위 영역으로 명확히 분리된다.
- `진행`에서는 결정 필요 Case가 실행 중 Case보다 먼저 보인다.
- Case 상태는 준비, 결정 필요, 허용됨, 실행 중, 결과 확인 중, 완료, 실패, 중지, 권한 회수로 구분된다.
- 상태 수와 마지막 변화 시각이 보인다.
- 완료된 Case는 기록으로 이동하지만 검색과 필터로 다시 찾을 수 있다.

#### 이야기 5.2 — Case 상세와 보조 채팅 사용하기

사용자로서, Case의 진행 근거와 타임라인을 확인하고 필요한 경우 그 Case에만 적용되는 대화를 이어가고 싶다.

수용 기준:

- 상세 화면에 Case가 생긴 이유, 근거, 계획, 정책, 외부 동작과 결과 확인 상태가 보인다.
- 타임라인은 안전하게 완료된 단계, 대기 중인 결정과 실패한 단계를 구분한다.
- 채팅 입력은 현재 Case에 귀속된다는 점이 보인다.
- 채팅으로 계획을 바꾸면 변경된 계획이 먼저 표시되고, 권한이나 결과가 달라지는 경우 재승인을 요구한다.
- 일반 명령을 새 Case로 만들고 싶을 때 현재 Case 대화와 구분할 수 있다.

#### 이야기 5.3 — 실제 결과가 확인된 뒤 완료하기

사용자로서, 외부 서비스가 요청을 받았다는 사실이 아니라 실제 결과가 반영되었는지 알고 싶다.

수용 기준:

- 요청 수락 후 결과를 아직 읽지 못했다면 상태가 `결과 확인 중`으로 남는다.
- 확인된 최종 값이나 생성된 항목이 완료 기록에 표시된다.
- 기대한 결과와 실제 결과가 다르면 완료가 아니라 예외 또는 실패로 표시된다.
- Google 작업은 생성되거나 수정된 실제 일정·할 일을 다시 열어 확인할 수 있다.
- SmartThings 동작은 명령 수락과 기기 상태 확인을 별도 단계로 보여 준다.

### Epic 6: 알림, 실패와 복귀

#### 이야기 6.1 — 필요한 때만 알림 받기

사용자로서, 모든 후보가 아니라 지금 판단하거나 대응해야 하는 일만 알림받고 싶다.

수용 기준:

- 새 후보 생성은 푸시 알림을 보내지 않고 `새 제안` 그룹 수만 갱신한다.
- 실행이 막힌 승인, 실패 또는 중요한 계획 변경은 즉시 알림 대상이 된다.
- 일반적인 정상 완료는 앱 내 기록과 묶음 요약을 기본으로 하며, 사용자가 즉시 알림을 요청했거나 중요한 결과인 경우에만 개별 알림을 보낸다.
- 여러 Case가 짧은 시간에 같은 이유로 막히면 하나의 묶음 알림으로 합칠 수 있다.
- 알림을 누르면 해당 Case의 정확한 결정 또는 실패 지점으로 이동한다.

#### 이야기 6.2 — 부분 실패를 이해하고 이어서 처리하기

사용자로서, 여러 단계 중 일부가 실패했을 때 이미 끝난 일과 남은 일을 구분하고 재시도하거나 중지하고 싶다.

수용 기준:

- 실패 화면에 성공, 실패, 실행 전 단계가 구분되어 보인다.
- 재시도할 때 중복 생성이나 중복 실행 가능성이 있으면 먼저 경고한다.
- 사용자는 실패 단계만 재시도, 대체 계획 검토 또는 전체 중지를 선택할 수 있다.
- 권한 만료나 연결 오류는 다시 연결해야 하는 서비스와 멈춘 동작을 정확히 보여 준다.
- 앱을 종료했다 다시 열어도 Case는 마지막 확인된 상태와 다음 가능한 동작을 유지한다.

### Epic 7: 정직한 연결 경계와 감사 기록

#### 이야기 7.1 — QuietPilot이 실제로 할 수 있는 범위 알기

사용자로서, 서비스 앱에 보이는 항목과 QuietPilot이 공개 연결을 통해 실제로 접근할 수 있는 항목을 구분하고 싶다.

수용 기준:

- 연결별 화면에 발견한 항목, 실행 가능한 항목과 접근 불가능한 항목이 구분된다.
- SmartThings 모바일 앱에 등록되어 있지만 공개 API에서 보이지 않는 개인 기기나 Routine을 제어 가능한 것으로 표시하지 않는다.
- 외부 서비스 오류로 목록이 불완전하면 완전한 목록처럼 표현하지 않는다.
- 각 외부 동작은 누가 또는 어떤 정책이 언제 허용했고 어떤 결과가 확인되었는지 기록한다.
- 권한을 회수해도 과거 감사 기록은 결과와 함께 남되 더 이상 새 데이터를 읽지 않는다.

## 네 가지 필수 Case 유형의 가시적 동작

### Connected-Signal Case

- 두 개 이상의 관련 신호를 하나의 목표로 묶는다.
- 카드와 상세 화면에서 각 출처와 연결 관계를 확인할 수 있다.
- 근거가 불충분하면 실행하지 않고 후보 또는 결정 필요 상태로 남는다.

### Direct-Delegation Case

- 사용자 명령이 즉시 하나의 Case가 된다.
- 에이전트가 연결된 맥락을 수집하고 내부 세부 작업을 대신 정리한다.
- 사용자에게는 하나의 계획, 필요한 권한과 핵심 결정만 보여 준다.

### Routine-Discovery Case

- 실제로 발견된 capability, 상태 또는 반복 패턴에서 Routine 후보를 만든다.
- 트리거, 조건, 동작과 해제 방법을 설명한다.
- 사용자가 명시적으로 활성화하기 전에는 자동 실행되지 않는다.

### Exception-And-Approval Case

- 충돌, 권한 부족, 실패, 중요한 변경 또는 고위험 동작이 발생하면 생성되거나 기존 Case가 이 상태로 전환된다.
- 이미 안전하게 완료한 일과 남은 결정을 하나의 카드로 압축한다.
- 사용자의 승인, 수정, 보류 또는 중지에 따라 정확한 중단 지점에서 이어지거나 종료된다.

## 빈 상태와 경계 사례

| 상황 | 기대 동작 |
| --- | --- |
| 연결된 서비스가 없음 | 가능한 연결과 각 연결로 얻을 수 있는 사용자 결과를 보여 주고, 직접 요청은 저장하되 필요한 연결 없이는 외부 실행하지 않는다. |
| 연결은 되었지만 후보가 없음 | 현재 발견 기준으로 분석과 후보 조회가 모두 성공했을 때만 연결별 `확인 완료·준비할 일 없음`을 표시하고, 확인한 기간·시각과 다음 확인 방식을 보여 준다. |
| 연결은 되었지만 후보 응답이 이전 발견 기준임 | `준비할 일 없음`으로 대체하지 않는다. 해당 연결에 `다시 확인 필요`와 재분석 동작을 표시한다. |
| 앱과 배포된 서버의 응답 계약이 호환되지 않음 | 정상 진행 상태로 포장하지 않는다. 해당 연결에 `확인 오류`를 표시하고, 서버 계약을 복구하기 전에는 결과나 `준비할 일 없음`을 확정하지 않는다. |
| 후보가 매우 많음 | 에이전트가 중복·유사 결과를 먼저 묶고 순위를 정한다. 첫 화면에는 그룹당 최대 세 개만 펼치며 고급 더 보기는 보조 경로로 둔다. |
| 중복 신호가 들어옴 | 기존 후보 또는 Case의 근거를 갱신하고 새 중복 카드를 만들지 않는다. |
| 결과나 실행 동작을 확실히 정할 수 없음 | Candidate를 만들지 않고 내부 보류한다. 새로운 근거나 capability가 생기면 다시 평가한다. |
| 숨긴 후보와 비슷한 후보가 다시 발견됨 | 단순 반복이면 억제하고, 새로운 중요한 근거가 있으면 달라진 점을 설명한 뒤 다시 제안할 수 있다. |
| 필요한 연결 없이 직접 요청함 | 가능한 분석·준비와 불가능한 실행을 나누고 필요한 연결을 제안한다. |
| 승인 뒤 계획이 바뀜 | 기존 승인을 무효화하고 변경 전후를 보여 준 뒤 재승인을 기다린다. |
| 실행 중 권한이 회수됨 | 다음 외부 동작 전에 정지하고 이미 완료된 결과와 취소되지 않는 영향을 보여 준다. |
| 일부 동작만 성공함 | 성공한 결과를 유지하고 실패 지점만 재시도하거나 전체 중지할 수 있게 한다. |
| 외부 결과를 확인하지 못함 | `완료`가 아니라 `결과 확인 중` 또는 `확인 실패`로 남긴다. |
| 앱을 닫았다 다시 엶 | 활성 Case, 연결 범위, 정책과 마지막 확인 상태를 복원한다. |
| 고위험 동작이 포함됨 | 반복 허용을 제공하지 않고 실행 직전 정확한 대상과 영향을 다시 승인받는다. |
| 서비스 앱에는 보이지만 API에는 없음 | 해당 항목을 `현재 접근 불가`로 표시하고 QuietPilot 기능으로 약속하지 않는다. |
| 문자에 미래 날짜와 과거 날짜가 함께 있음 | 자동 등록하지 않고 선택할 날짜와 해석 근거를 `결정 필요`로 보여 준다. |
| 문자에 OTP·결제·단축 URL·회신 유도가 있음 | 일정 후보보다 안전 격리를 우선하고 링크 열기·답장·결제·자동 알림을 실행하지 않는다. |
| 같은 예약 문자가 다시 도착함 | 발신자, 사건 유형, 정규화된 날짜·시간 fingerprint로 기존 Case/알림을 갱신하고 중복 생성하지 않는다. |
| 스팸 판별 모델과 규칙이 충돌함 | 자동 처리하지 않고 보수적인 `검토 필요`로 내리며 평가용 익명화 오류 유형만 기록한다. |

## 시각·상호작용 요구사항

- 모바일이 기본 화면이며 카드와 그룹 중심으로 동작한다.
- 최상위 작업 영역은 `진행`과 `새 제안` 두 개뿐이다.
- 채팅은 전역 직접 요청 또는 Case별 보조 입력으로 사용하며 홈의 주 인터페이스가 아니다.
- 정보 밀도는 높일 수 있지만 제목, 상태, 이유, 근거, 위험, 권한과 다음 동작의 계층이 명확해야 한다.
- 다크 모드와 라이트 모드는 별도 모드로 제공할 수 있으며 상태 의미는 두 모드에서 동일해야 한다.
- 색은 실행, 승인, 성공, 실패처럼 기능적인 상태를 나타내는 데만 사용하고 과도한 광택, 그라데이션과 장식은 피한다.
- 친근한 말투를 사용하되 위험과 권한 설명은 모호하게 완화하지 않는다.
- 마스코트는 MVP에 포함하지 않는다.
- 현재 생성된 시각안 중 하나를 최종 디자인으로 고정하지 않는다. 공통 정보 구조와 상호작용만 PRD 요구사항으로 채택한다.

## 우리가 만드는 것

- 로그인 또는 가입과 선택적 서비스 연결 흐름
- 연결별 읽기·실행 범위와 API 가시성 설명
- 최근 7일 기본 분석과 이후 새 신호의 점진적 발견
- `진행`과 `새 제안`으로 나뉜 모바일 Case 화면
- 실행 준비된 새 제안의 결과별 묶음, 한 번의 결정과 펼쳐 보는 설명
- 승인·수정·숨김·중지와 검증 결과를 이용한 설명 가능한 발견 개인화. 관련성 학습은 실행 권한과 분리한다.
- Connected Signal, Direct Delegation, Routine Discovery, Exception/Approval 네 Case 유형
- 결과 중심 Case 카드, 상세 타임라인과 Case별 보조 채팅
- 한 번, 조건부, 반복 허용과 고위험 영구 승인 경계
- 계획 변경 시 승인 무효화와 변경 전후 재확인
- 실패, 부분 성공, 재시도, 중지와 권한 회수 흐름
- 후보와 일반 완료 알림을 줄이고 필요한 결정만 방해하는 알림 정책
- 실제 Gmail 입력과 실제 Google Calendar 또는 Tasks의 가역적 동작
- 공개 API에 보이는 SmartThings capability·상태 발견
- 별도 시연 승인을 받은 SmartThings 명령 한 번과 결과 상태 확인
- 외부 요청 수락과 실제 완료를 구분하는 감사 기록
- 문자 안전 분석과 미래 일정 자동 알림의 로컬 프로토타입. 실제 SMS 권한·알림 side effect는 배포 정책과 실기기 검증 전까지 포함하지 않는다.

## 더 시간이 있다면 추가할 것

- Google Drive와 Docs에 장기 보관되는 준비 문서와 브리프
- Android 위치와 지오펜스를 활용한 추가 생활 맥락
- 더 많은 이메일, 일정, 생산성 및 IoT 연결
- 장기간 행동에 따른 더 정교한 발견·묶음·순위 개인화
- 사용자가 고르는 일간·주간 완료 요약과 알림 묶음 설정
- 여러 기기 간 동기화와 웹 관제 화면
- Google Play 허용 경로가 증명된 Android SMS history 연결, 향후 문자 관찰, 온디바이스 분류 모델과 실제 로컬 알림 등록
- 충분한 동의 기반 평가셋이 쌓인 뒤 스팸·스미싱/일정 판별 모델의 파인튜닝과 calibration. 원문 문자 자동 수집은 포함하지 않는다.
- 가정 구성원별 권한, 공동 승인과 공유 Routine
- 고급 정책 시뮬레이션과 실행 전 영향 미리보기
- 작업 핵심 경로를 늦추지 않는 범위의 AgentCore 배포와 관측성

## 명시적 비목표

- 사용자가 모든 트리거와 동작을 직접 만드는 범용 자동화 빌더
- 사용자가 매번 긴 대화를 주도해야 하는 일반 챗봇
- 숨은 권한 확장이나 승인 없는 고위험 실행
- 실제 연결 대신 시각 mock만으로 동작을 증명하는 데모
- 특정 여행, 귀가, 취침 Routine을 제품에 하드코딩하고 발견 기능처럼 표현하는 것
- 모든 SmartThings 등록 기기와 모바일 Routine을 공개 API로 제어할 수 있다고 주장하는 것
- 첫 제출에서 모든 서비스와 모든 기기 종류를 지원하는 것
- 결제, 구매, 삭제, 민감정보 전송과 최종 제출의 무승인 자동화
- 프로덕션 규모의 다중 테넌트, 과금과 조직 관리

## 제출 증명 포인트

1. 사용자가 실제 계정을 연결하고 QuietPilot이 접근 가능한 capability와 접근 불가능한 항목을 구분해 보여 준다.
2. 관련 없는 인사 메일은 아무 Candidate도 만들지 않고, 마감 메일은 지원되는 `할 일 준비` Action이 있는 Candidate 하나를 만든다.
3. 사용자는 결과별 묶음 안의 카드에서 준비할 동작을 먼저 보고 `이대로 준비`, `내용 조정`, `필요 없음` 중 하나를 고른다.
4. 실제 관련 신호로 Connected-Signal Case를 만들고 직접 요청으로 Direct-Delegation Case를 만든 뒤 같은 Case 구조에서 보여 준다.
5. 실제 capability에서 여러 Routine 후보를 발견하되 자동 활성화하지 않는 모습을 보여 준다.
6. 선택한 후보를 설명 가능한 계획으로 만들고 한 번 또는 조건부 권한을 선택한다.
7. 실제 Google Calendar 또는 Tasks 동작을 수행하고 생성·변경 결과를 다시 읽어 완료를 확인한다.
8. 실행 내용이 바뀌었을 때 기존 승인이 무효화되고 변경 전후를 보여 주는 Exception/Approval 흐름을 보여 준다.
9. IoT 동작은 시연 시점의 별도 명시적 승인 후 한 번 실행하고, SmartThings 명령 수락과 실제 기기 상태 확인을 구분한다.
10. 진행 타임라인, 실패·재시도, 보류·중지, 권한 회수와 기록을 한 흐름에서 보여 준다.
